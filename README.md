# mylb — учебный балансировщик нагрузки на Python

TLS 1.3 · health-check'и · least connections · sticky sessions · JSON-логи · метрики Prometheus · admin API

Только стандартная библиотека Python 3.9+, **устанавливать ничего не нужно**.

## Как это устроено

```
                 HTTPS (TLS 1.3)                 обычный HTTP
  клиент  ───────────────────────►  mylb  ───────────────────────►  backend 1
 (curl,           :8443            │  │  │                          backend 2
  браузер)                         │  │  └─ выбор бэкенда           backend 3
                                   │  └──── health-check'и (раз в 2 с)
  Prometheus ◄─── :9100/metrics ───┘
  оператор   ───► :9101 admin API        (бэкенды, сертификат, настройки — без перезапуска)
```

Путь запроса:

1. Клиент устанавливает TLS-соединение. Версии ниже 1.3 отклоняются на рукопожатии.
2. Есть cookie `LB_BACKEND`, указывающая на живой и не перегруженный бэкенд → берём его (**sticky**).
3. Иначе берём живых и сортируем по числу активных запросов, побеждает наименее загруженный (**least connections**). При равной нагрузке бэкенды чередуются.
4. Если у бэкенда уже `--max-conns` активных запросов, он считается перегруженным и пропускается.
5. Никого не нашли → `503` и `lb_rejected_total++`.
6. Проксируем запрос, пишем access-лог и обновляем метрики.

## Ключевые понятия

**TLS termination.** Шифрование заканчивается на балансировщике, до бэкендов трафик идёт обычным HTTP. Сертификаты хранятся в одном месте, бэкендам не нужно заниматься шифрованием. Если сеть до бэкендов не доверенная, TLS добавляют и на этом участке.

**Активные health-check'и.** Раз в `--health-interval` LB делает `GET /healthz` на каждый бэкенд, ответ 2xx значит здоров. Состояние меняется только после серии одинаковых результатов (2 подряд, константы `RISE` и `FALL` в `backend.py`). Иначе один случайный таймаут вызывает «флаппинг».

**Пассивные проверки.** Если реальный запрос к бэкенду упал (отказ соединения, таймаут), бэкенд сразу выводится из ротации, не дожидаясь следующей активной проверки. Вернёт его уже health-check.

**Least connections.** Лучше простого round-robin, когда запросы разной длительности. «Загруженность» здесь это число одновременных запросов, порог задаётся `--max-conns`. В реальных системах бывают и более умные метрики: латентность, CPU, очередь.

**Sticky sessions.** LB ставит cookie с id бэкенда, и дальше клиент попадает на тот же сервер. Нужно, если бэкенд хранит сессию у себя в памяти. В cookie лежит хеш-id, а не `ip:port`, чтобы не светить внутреннюю топологию. Если «прилипший» бэкенд умер или перегружен, клиента перекинет на другой и выдаст новую cookie.

**Потоки и гонки.** Сервер многопоточный: на каждое соединение свой поток. Общие данные (счётчик активных запросов, метрики) меняют сразу много потоков, поэтому они защищены `threading.Lock`. Загляни в `Backend.try_acquire`: проверка лимита и увеличение счётчика сделаны под одним локом именно чтобы избежать гонки.

**Логи и метрики.** Логи отвечают на вопрос «что случилось с этим запросом?», метрики на вопрос «как у системы дела в целом?». Нужны оба. Формат метрик Prometheus это обычный текст, его генерирует `mylb/metrics.py` (можешь открыть и посмотреть, магии там нет).

## Запуск

Нужны Python 3.9+ и openssl (или пропусти этот раздел и сразу переходи к «Запуск в Docker»).

```bash
bash scripts/gen-cert.sh        # самоподписанный сертификат → certs/
python3 -m unittest             # тесты (по желанию; тестам admin API нужен openssl)
```

Дальше три терминала (все в папке проекта):

```bash
# терминал 1 — три тестовых бэкенда (порты 9001-9003; другое число: bash scripts/demo-backends.sh 5)
bash scripts/demo-backends.sh

# терминал 2 — балансировщик (логи побегут сюда)
export MYLB_ADMIN_TOKEN=my-secret-token     # любой свой; в настоящей системе длинный и случайный
python3 -m mylb

# терминал 3 — эксперименты
```

Все параметры: `python3 -m mylb --help`.

### Добавляем бэкенды

Список бэкендов нигде не зашит: ни в коде, ни в конфиге. Балансировщик стартует с пустым пулом и пишет в лог `пул пуст`. Пока бэкендов нет, клиенты получают `503`. Бэкенды добавляют и удаляют запросами к admin API, перезапуск не нужен.

В терминале 3 задай тот же токен и короткую команду `api`, чтобы не повторять заголовки:

```bash
export MYLB_ADMIN_TOKEN=my-secret-token
A=http://127.0.0.1:9101/v1
api() { curl -sS -H "Authorization: Bearer $MYLB_ADMIN_TOKEN" -H "Content-Type: application/json" "$@"; echo; }
```

Теперь добавь три запущенных бэкенда и посмотри список:

```bash
for port in 9001 9002 9003; do
  api -X POST $A/backends -d "{\"url\": \"http://127.0.0.1:$port\"}"
done
api $A/backends
```

На каждый `POST` приходит `201` и `"alive": true`. Удалить бэкенд: `api -X DELETE $A/backends/ID -i` (вместо `ID` подставь `id` из списка).

Добавлять можно только сервер, который уже запущен и отвечает. Запрос не создаёт сервер, он сообщает балансировщику адрес. Если по адресу никого нет, бэкенд попадёт в пул с `"alive": false` и трафик получать не будет.

Список сохраняется в файле `mylb-state.json`, поэтому после перезапуска балансировщика добавлять бэкенды заново не нужно. Этот файл балансировщик ведёт сам, руками его не редактируют. Начать с чистого листа: удали бэкенды через API или останови балансировщик и удали файл.

Без admin API (переменная `MYLB_ADMIN_TOKEN` не задана) список можно передать только флагом: `python3 -m mylb --backends http://127.0.0.1:9001,http://127.0.0.1:9002`. Менять его тогда получится только перезапуском. Без токена и без флага балансировщик не запустится и объяснит почему.

## Эксперименты: проверяем, что всё работает

**1. TLS 1.3 включён, старые версии отклоняются**
```bash
curl -sk --tlsv1.3 https://localhost:8443/        # ответ от какого-то бэкенда
curl -sk --tls-max 1.2 https://localhost:8443/    # ошибка рукопожатия — так и задумано
```
(`-k` нужен, потому что сертификат самоподписанный.) В access-логе будет `"tls": "TLSv1.3"`, а отказ клиента с TLS 1.2 виден как «соединение отклонено».

**2. Распределение нагрузки без cookie**
```bash
for i in $(seq 6); do curl -sk https://localhost:8443/; done
```
При равной нагрузке бэкенды чередуются.

**3. Sticky sessions**
```bash
for i in $(seq 6); do curl -sk -c /tmp/jar -b /tmp/jar https://localhost:8443/; done
```
Все ответы от одного бэкенда. Файл `/tmp/jar` это «браузерные» cookie.

**4. Проверки здоровья**
```bash
curl http://127.0.0.1:9002/toggle-health     # b2 теперь отвечает 503 на /healthz
```
Секунд через 5 в логе LB появится `состояние бэкенда изменилось ... "alive": false`, и b2 перестанет получать трафик. Повторный вызов `toggle-health` вернёт его (тоже через несколько секунд). Можно ещё остановить один бэкенд через Ctrl+C и посмотреть на пассивную проверку.

**5. Перегрузка**

Уменьши порог через admin API: теперь 3 бэкенда по 5 слотов, всего 15.
```bash
api -X PATCH $A/settings -d '{"max_conns": 5}'
for i in $(seq 30); do curl -sk -o /dev/null -w "%{http_code}\n" https://localhost:8443/slow & done | sort | uniq -c
```
Результат: 15 ответов `200` и 15 ответов `503`, потому что все живые бэкенды заняты. Пока идёт тест, смотри `curl -s localhost:9100/metrics | grep active`. Вернуть как было: `api -X PATCH $A/settings -d '{"max_conns": 100}'`.

**6. Плавная остановка**

Запусти `curl -sk https://localhost:8443/slow` и сразу нажми Ctrl+C в терминале с LB. Запрос дойдёт до конца (`200`), и только потом LB завершится.

## Admin API: управление без перезапуска

Бэкенды, TLS-сертификат и настройки можно менять на работающем балансировщике. Идущие запросы при этом не обрываются. Полный контракт (все поля, коды ответов и ошибок) лежит в `docs/admin-api.openapi.yaml`.

| Что | Запрос |
|---|---|
| список бэкендов | `GET /v1/backends` |
| добавить бэкенд | `POST /v1/backends` |
| один бэкенд | `GET /v1/backends/{id}` |
| вывести из ротации или вернуть | `PATCH /v1/backends/{id}` |
| удалить бэкенд | `DELETE /v1/backends/{id}` |
| сведения о сертификате | `GET /v1/tls/certificate` |
| загрузить новый сертификат и ключ | `PUT /v1/tls/certificate` |
| перечитать сертификат с диска | `POST /v1/tls/certificate/reload` |
| текущие настройки | `GET /v1/settings` |
| изменить настройки | `PATCH /v1/settings` |
| сетевые интерфейсы машины | `GET /v1/system/interfaces` |

Как это устроено:

- **Отдельный порт.** `--admin`, по умолчанию `127.0.0.1:9101`. Через клиентский `:8443` до управления не добраться.
- **Токен.** Admin API включается, только если задана переменная окружения `MYLB_ADMIN_TOKEN`. Каждый запрос несёт заголовок `Authorization: Bearer <токен>`. Без переменной admin API выключен: порт закрыт, файл состояния не читается, а бэкенды нужно передать флагом `--backends`.
- **Файл состояния.** Всё, что добавили, удалили и изменили через API, записывается в `mylb-state.json` (флаг `--state-file`) и переживает перезапуск. Пока файл есть, флаги `--backends`, `--max-conns`, `--health-path` и `--health-interval` не используются.
- **Сначала диск, потом память.** Если изменение не удалось записать, оно не применяется, а ответ будет `500 persist_failed`.
- **Ошибки** приходят в формате `application/problem+json` с машинным полем `code`.

### Пробуем

Балансировщик уже запущен с токеном, а команда `api` задана в разделе «Добавляем бэкенды».

**1. Список бэкендов**
```bash
api $A/backends
```
У каждого бэкенда есть `id`. Он нужен для следующих команд, и он же лежит в sticky-cookie.

**2. Добавить ещё один бэкенд**
```bash
python3 demo_backend.py --addr 127.0.0.1:9004 --name b4 &      # сначала сам сервер
api -X POST $A/backends -d '{"url": "http://127.0.0.1:9004"}'
for i in $(seq 8); do curl -sk https://localhost:8443/; done      # среди ответов появился b4
```
Ответ `201` и `"alive": true`: проверка здоровья выполняется сразу. Повтор той же команды вернёт `409 backend_exists`.

**3. Вывести бэкенд из ротации и вернуть**
```bash
api -X PATCH $A/backends/ID -d '{"state": "draining"}'     # вместо ID подставь id из списка
api -X PATCH $A/backends/ID -d '{"state": "active"}'
```
`draining` значит «новых запросов не давать». Запросы, которые бэкенд уже обрабатывает, дойдут до конца.

**4. Удалить бэкенд**
```bash
api -X DELETE $A/backends/ID -i        # 204 No Content
```

**5. Настройки**
```bash
api $A/settings
api -X PATCH $A/settings -d '{"max_conns": 5}'
```
Меняются только переданные поля, перезапуск не нужен. Так же меняется порог в эксперименте «Перегрузка».

**6. Заменить сертификат**
```bash
api $A/tls/certificate                                   # запомни fingerprint_sha256
CERT_DIR=/tmp/newcert bash scripts/gen-cert.sh           # новая пара "сертификат + ключ"
python3 -c 'import json,sys; print(json.dumps({"cert_pem": open(sys.argv[1]).read(), "key_pem": open(sys.argv[2]).read()}))' \
  /tmp/newcert/server.crt /tmp/newcert/server.key | api -X PUT $A/tls/certificate -d @-
```
В ответе новый `fingerprint_sha256` и `"source": "upload"`. Приватный ключ в ответах не возвращается никогда. Проверить, что клиенты действительно получают новый сертификат:
```bash
echo | openssl s_client -connect localhost:8443 2>/dev/null | openssl x509 -noout -fingerprint -sha256 | tr -d ':' | tr 'A-F' 'a-f'
```
Файлы `certs/server.crt` и `certs/server.key` при этом заменены, так что после перезапуска сертификат останется новым. Если пара негодная (сертификат и ключ не совпадают, файл повреждён, ключ с паролем), ответ будет `422`, а балансировщик продолжит работать со старым сертификатом.

**7. Перечитать сертификат с диска**

Если файлы заменил кто-то другой (например, certbot):
```bash
api -X POST $A/tls/certificate/reload
```

**8. Сеть машины**

Балансировщик может показать сетевые интерфейсы машины и их адреса. Сам он их не собирает: это делает скрипт, который запускают на машине, а балансировщик читает готовый файл `hostinfo/host.json`.
```bash
bash scripts/host-info.sh            # собрать (Linux: команда ip, macOS: ifconfig)
api $A/system/interfaces
```
В ответе `items` с именами интерфейсов, адресами и длиной префикса подсети, а `collected_at` показывает, когда сведения собраны. Это снимок: если адреса поменялись, запусти скрипт ещё раз, перезапускать балансировщик не нужно. Пока скрипт не запускали, ответ будет `404 host_info_missing`.

**9. Перезапуск**

Останови балансировщик (Ctrl+C) и запусти снова той же командой. Бэкенды, `max_conns` и сертификат на месте: они прочитаны из `mylb-state.json` и из файлов сертификата.

**10. Ошибки**
```bash
curl -s $A/backends                                           # 401: нет токена
api -X POST $A/backends -d '{"url": "https://b4:9000"}'       # 422: в errors сказано, какое поле не так
api -X PATCH $A/settings -d '{"max_conns": 0}'                # 422, и ничего не изменилось
```

### Admin API в Docker

Адрес тот же, `http://127.0.0.1:9101/v1`, но бэкенды называются по именам сервисов: `http://b1:9000`. Подробности в разделе «Запуск в Docker».

### Что в admin API упрощено

- **Нет TLS на самом admin-порту.** Поэтому он слушает только на loopback (в Docker порт проброшен только на `127.0.0.1`). Открывать его в сеть в таком виде нельзя: по нему передаётся приватный ключ.
- **Один токен на всё**, без роли «только чтение».
- **Нет ограничения частоты запросов** (rate limiting): подбор токена ничем не замедляется.
- **Нет автоматического подхвата** сертификата при замене файлов: нужен запрос `reload`. Автоматику описывает спека `specs/001-tls-cert-hot-reload`.
- Сведения о сертификате (срок, имена) читаются внутренней функцией модуля `ssl`: в стандартной библиотеке нет публичного способа разобрать сертификат из файла.

## Запуск в Docker (всё одной командой)

Нужен Docker с `docker compose` (Docker Desktop на Windows/macOS или Docker Engine на Linux). Python и openssl на хосте не нужны.

```bash
cp .env.example .env       # один раз; открой .env и впиши свой токен admin API
bash scripts/up.sh --build
docker compose ps          # все сервисы должны быть running/healthy
```

`scripts/up.sh` делает четыре вещи: собирает сведения о сети машины в `hostinfo/host.json`, проверяет `LB_BIND` (если задан), передаёт в контейнер основной адрес машины переменной `HOST_IP` и выполняет `docker compose up -d`. Проверить переменную: `docker compose exec lb printenv HOST_IP`. Его аргументы передаются в `docker compose up`. Обычный `docker compose up --build -d` тоже работает, но сведения о сети тогда не обновятся.

Токен обязателен: без admin API в балансировщик нельзя добавить бэкенды. Файл `.env` compose читает сам, в git он не попадает. Если токена нет, `docker compose` сразу остановится и скажет об этом.

Балансировщик стартует с пустым пулом. Серверы `b1`–`b4` уже запущены, но балансировщик о них не знает. Добавь их через admin API:

```bash
set -a; . ./.env; set +a        # берём токен из .env в текущий терминал
A=http://127.0.0.1:9101/v1
api() { curl -sS -H "Authorization: Bearer $MYLB_ADMIN_TOKEN" -H "Content-Type: application/json" "$@"; echo; }

for name in b1 b2 b3; do
  api -X POST $A/backends -d "{\"url\": \"http://$name:9000\"}"
done
api $A/backends                 # три бэкенда, у каждого "alive": true
```

Адрес бэкенда здесь это имя сервиса из `docker-compose.yml` и порт **9000**: так сервер виден внутри docker-сети. Порты `9001`–`9004` существуют только на твоей машине, балансировщик в контейнере их не видит. Четвёртый сервер `b4` оставлен свободным, чтобы попробовать добавление и удаление. 
**Ещё серверы, с любыми именами.** Запрос `POST /v1/backends` не создаёт сервер, он только сообщает балансировщику адрес. Поэтому новый бэкенд это два шага: запустить контейнер и добавить его адрес. Скрипт `scripts/backend.sh` делает оба шага, `docker-compose.yml` при этом не меняется:

```bash
bash scripts/backend.sh add b5              # docker run + POST /v1/backends {"url": "http://b5:9000"}
bash scripts/backend.sh add b6 shop         # сразу несколько
bash scripts/backend.sh list                # что сейчас в пуле
bash scripts/backend.sh remove b5           # DELETE в балансировщике, потом удаление контейнера
```

Имя может быть любым из строчных латинских букв, цифр и дефиса. Токен скрипт берёт из `MYLB_ADMIN_TOKEN` или из `.env`. Такие контейнеры живут вне compose, поэтому `docker compose down` их не останавливает: убирай их командой `remove`.

Список бэкендов и настройки лежат в томе `state`, поэтому переживают `docker compose down` (но не `down -v`).

Что поднимется:

| Сервис | Что это | Адрес на вашей машине |
|---|---|---|
| `certgen` | одноразовая задача: делает сертификат в общий том и завершается | — |
| `b1`, `b2`, `b3`, `b4` | тестовые серверы; в балансировщик добавляются через admin API | `http://localhost:9001`, `9002`, `9003`, `9004` |
| `lb` | балансировщик (TLS 1.3) | `https://localhost:8443`, метрики `http://localhost:9100/metrics`, admin API `http://localhost:9101` |
| `prometheus` | собирает метрики с `lb:9100` | `http://localhost:9090` |
| `grafana` | готовый дашборд «mylb» | `http://localhost:3000` |

Все порты привязаны к `127.0.0.1`, то есть из вашей сети стенд не виден. Клиентский порт 8443 можно открыть на другом сетевом интерфейсе машины: впиши в `.env` строку `LB_BIND=192.168.1.10` (IP нужного интерфейса; все свои адреса покажет `bash scripts/host-info.sh`) или `LB_BIND=0.0.0.0` (все интерфейсы) и выполни `bash scripts/up.sh`. Метрики и admin API всегда остаются на `127.0.0.1`: у admin API нет TLS.

Какие адреса есть на машине, показывает сам стенд: `bash scripts/up.sh` печатает их при запуске, а admin API отдаёт в `GET /v1/system/interfaces`. Контейнер сеть машины не видит, поэтому сведения собирает скрипт на машине и передаёт балансировщику через папку `hostinfo/`. Если в `LB_BIND` вписан адрес, которого на машине нет, `up.sh` остановится и скажет об этом до запуска Docker. Внутри docker-сети сервисы находят друг друга по именам (`b1`, `lb`, `prometheus`): за это отвечает встроенный DNS Docker, поэтому бэкенд добавляют как `http://b1:9000`, а не по IP-адресу.

Когда бэкенды добавлены, эксперименты из раздела выше работают без изменений, адреса те же:

```bash
curl -sk --tlsv1.3 https://localhost:8443/            # TLS 1.3
curl -sk --tls-max 1.2 https://localhost:8443/        # отказ
for i in $(seq 6); do curl -sk https://localhost:8443/; done
for i in $(seq 6); do curl -sk -c /tmp/jar -b /tmp/jar https://localhost:8443/; done   # sticky
```

Что меняется по сравнению с запуском вручную:

- **Логи** смотрим так: `docker compose logs -f lb`.
- **Health-check.** `curl http://localhost:9002/toggle-health` работает как раньше. Бэкенд можно и «убить по-настоящему»: `docker compose stop b2`, вернуть через `docker compose start b2`. Следи за `docker compose logs -f lb` и на дашборде Grafana: панель «Бэкенды» покраснеет.
- **Перегрузка.** Порог меняется через admin API, как и при запуске вручную:
  ```bash
  api -X PATCH $A/settings -d '{"max_conns": 5}'
  for i in $(seq 30); do curl -sk -o /dev/null -w "%{http_code}\n" https://localhost:8443/slow & done | sort | uniq -c
  ```
  Ожидаем 15 × `200` и 15 × `503`; в Grafana видны рост `503` и заполненные слоты. Вернуть как было: `api -X PATCH $A/settings -d '{"max_conns": 100}'`.
- **Плавная остановка.** Запусти `curl -sk https://localhost:8443/slow` и сразу `docker compose stop lb`: запрос должен дойти до конца с `200`. Docker шлёт `SIGTERM`, и именно поэтому в коде есть обработчик сигнала. В `docker-compose.yml` стоит `stop_grace_period: 20s`: LB дожидается запросов до 15 с, а при стандартных 10 с Docker убил бы его раньше.
- **Метрики.** В Prometheus (`localhost:9090`) работают те же PromQL-запросы из раздела ниже. Метки бэкендов здесь выглядят как `b1:9000` (имя сервиса и внутренний порт), потому что LB ходит к ним по docker-DNS.

Остановка: `docker compose down` (тома с сертификатом, списком бэкендов и данными Prometheus/Grafana останутся). Начисто: `docker compose down -v`.

**Заметки для обучения**

- Один образ `mylb:local` используется и для LB, и для бэкендов: там нет зависимостей, а запускаемая команда переопределяется.
- Процессы работают не от root (пользователь `app`), а `init: true` ставит минимальный init-процесс (`tini`) как PID 1. Без него Python в роли PID 1 игнорирует `SIGTERM`, и `docker stop` ждёт 10 с до принудительного убийства.
- LB не зависит от бэкендов (`depends_on` у него только на `certgen`): он стартует с пустым пулом, а серверы добавляют позже. В настоящих системах так и бывает: серверы появляются и исчезают, а балансировщик узнаёт о них через API или service discovery.
- Том с сертификатом создаёт root, а LB работает не от root. Поэтому задача `certgen` отдаёт каталог пользователю LB (uid 10001), и закрытый ключ получает права 600: его читает только владелец. Право записи в каталог нужно admin API, чтобы заменять сертификат. В реальной жизни секреты передают через Docker/Kubernetes secrets.
- Grafana запущена без логина, так как порт открыт только на localhost. Не выставляй её так в интернет.

## Prometheus

Метрики лежат на `http://127.0.0.1:9100/metrics`. Запуск локального Prometheus (Linux):

```bash
docker run --network host -v $PWD/prometheus.yml:/etc/prometheus/prometheus.yml prom/prometheus
```

Интерфейс откроется на `http://localhost:9090`. На macOS/Windows `--network host` работает иначе: запускай LB с `--metrics 0.0.0.0:9100` и в `prometheus.yml` указывай `host.docker.internal:9100`.

Метрики: `lb_requests_total{backend,code}`, `lb_request_duration_seconds` (гистограмма), `lb_backend_up`, `lb_backend_active_connections`, `lb_rejected_total`, `lb_health_checks_total{backend,result}`.

Полезные запросы (PromQL):

```promql
lb_backend_up                                                              # кто жив
sum by (backend) (rate(lb_requests_total[1m]))                             # RPS по бэкендам
sum(rate(lb_requests_total{code=~"5.."}[5m])) / sum(rate(lb_requests_total[5m]))   # доля ошибок
histogram_quantile(0.95, sum by (le) (rate(lb_request_duration_seconds_bucket[5m])))  # p95
lb_backend_active_connections                                              # текущая нагрузка
```

## Что осознанно упрощено

- **Нет HTTP/2** (только HTTP/1.1), нет WebSocket и стриминга: ответ бэкенда целиком читается в память и потом отдаётся клиенту.
- **Тело запроса** до 10 МБ, `Transfer-Encoding: chunked` в запросах не поддерживается (ответ `411`).
- **Многопоточная модель** проще для понимания, но под десятки тысяч одновременных соединений Python не подходит; там берут `asyncio` (aiohttp) или вообще не пишут балансировщик на Python.
- **Метрики написаны руками** ради обучения. В реальном проекте ставят `prometheus_client`: API очень похож (`Counter`, `Gauge`, `Histogram`), плюс он отдаёт метрики процесса.
- Sticky-cookie не подписана: подделав id, клиент выберет бэкенд сам.
- Нет повторных попыток (retry): если бэкенд упал посреди запроса, клиент получит 502.
- Один экземпляр LB: сам он тоже может упасть. Сертификат самоподписанный.
- Упрощения admin API перечислены в его разделе.
